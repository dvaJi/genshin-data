# Data pipeline & validation

This package's `src/data/**` is generated by [format-genshindata](../format-genshindata) and published to npm as `genshin-data`. This file documents how the data gets here and how to verify it.

## Data flow

```
GenshinData/ExcelBinOutput + TextMap        (Dimbreath dump, not committed)
        │  node index.js  (LANG_TOFORMAT=EN,VI,PT,...)
        ▼
format-genshindata/readable/<lang>/         (generated output)
        │  node scripts/sync-data.mjs --from ../format-genshindata/readable
        ▼
genshin-impact-data/src/data/<lang>/        (committed here)
        │  pnpm generate  ->  src/min/*.min.json  (bundled per collection)
        │  pnpm build     ->  dist/              (published)
        ▼
npm: genshin-data
```

`pnpm generate` (called by `prepublishOnly`) bundles each collection into
`src/min/data_<lang>_<folder>.min.json`; `pnpm build` produces `dist/`.

## Validation

### `pnpm validate-data` (a.k.a. `scripts/validate-data.mjs`)

Runtime validation of `src/data/**` against the zod schemas in `scripts/schemas.mjs`. The
TypeScript interfaces in `src/types/` cannot do this job: they are compile-time only and the
data is loaded from JSON at runtime, so a broken generator (a stale dump anchor, a renamed
column) produces structurally wrong JSON that still type-checks fine.

Checks performed:

| category | blocking | what it catches |
| --- | --- | --- |
| `schema` | yes | entry does not match its zod schema (wrong/missing fields, wrong types) |
| `filename` | yes | `<id>.json` does not match the entry's `id` — the loader looks files up by name, so a mismatch silently hides the entry |
| `parity` | yes | a language is missing ids that english has — surfaces as `undefined` for consumers, not as an error |
| `reference` | yes | `domains.json` rotation ids that do not exist in `characters/` or `weapons/` |
| `io` | yes | unparseable JSON |
| `duplicate` | no | two files sharing a `_id` (stale leftovers from an older dump generation) |
| `unresolved` | no | empty localized `name`, or a nested skill whose `id` slug resolved to `""` |

Useful flags: `--lang english`, `--folders characters,weapons`, `--max-errors N`, `--json report.json`.
Exit code is non-zero only for blocking categories, so CI fails on real breakage but not on the
known upstream TextMap gaps.

### `pnpm check-changelog` (a.k.a. `scripts/check-changelog.mjs`)

Answers "is this data actually current?" by asking yatta.moe what shipped in a game version and
confirming each new entity exists locally.

```bash
node scripts/check-changelog.mjs                # latest version on yatta
node scripts/check-changelog.mjs --version 7.1
node scripts/check-changelog.mjs --lang english
```

The endpoint is `GET https://gi.yatta.moe/api/v2/static/changelog` — **no language segment and
no query parameters**; it returns every version at once, keyed by a dotless string
(`data["71"].version === "7.1"`), and `?version=` is silently ignored. It uses the legacy
`{response, data}` envelope, unlike the entity endpoints which use `{code, data}`.

Two traps this script works around:

- yatta ids are its own and do **not** match the dump's numeric ids (yatta food `132029` vs a
  dump food-id ceiling of `5502`), so entities are matched by **name**, not id.
- `GET /api/v2/en/<endpoint>?ids=...` is only honoured by some endpoints. `furniture` ignores the
  filter and returns the whole table. The per-id route `/api/v2/en/<endpoint>/<id>` is reliable,
  so unresolved ids fall back to one detail request each.

## Syncing from format-genshindata

```bash
node scripts/sync-data.mjs --from ../format-genshindata/readable            # add/update only
node scripts/sync-data.mjs --from ../format-genshindata/readable --dry-run
node scripts/sync-data.mjs --from ../format-genshindata/readable --prune    # also delete removed slugs
```

**`--prune` is opt-in and absence alone never triggers a delete.** This is deliberate: a
generator that produces 0 files for a folder (stale dump anchor, crashed run) looks exactly like
"upstream deleted everything", and acting on that wiped 32,712 files in one pass. The script
refuses to prune a source folder that is empty or missing, skips languages with no output at all,
and tolerates files vanishing mid-scan (the pipeline rewrites `readable/` live).

Before syncing, confirm the upstream run covered every language and finished — each language
directory is cleared at the start of its own pass, so a language that was skipped or that died
mid-run is left empty rather than stale.

## Known data gaps (upstream, not bugs here)

- `exaiphanes_blade` (weapon `11521`) has no ascension materials: the dump ships
  `costItems: [{}, {}, {}]` on every `WeaponPromoteExcelConfigData` row for it, so `ascensions[].materials`
  is empty and the weapon is absent from the weapon domain rotations.
- 4 of the 7 foods added in 7.1 (`Iridescent Aria`, `Hoarfrost Soup`, `Vesna-Themed Ice Cream`,
  `Vodyanitsa-Themed Ice Cream`) are absent from the dump's `CookRecipeExcelConfigData` (the
  materials exist in `MaterialExcelConfigData` but nothing references them as a recipe output).
- Three stale duplicate-`_id` pairs remain from older generations, present in all 15 languages:
  `food/consomme` + `food/consomm` (3413), `food/sour_sauce_kipper` + `food/sour_sauce_ceviche`
  (2502), `geography/tower_piercing_into_the_sky` + `..._at_the_sky` (70800019). The current dump
  only emits one of each; the other is a leftover that `--prune` removes.
- A few placeholder furnishings (`Ceiling 1`, `Wall 1`, `Test Grill`) have no IT/TR
  localization, so their `name` is an empty string.
- `chinese-simplified` has 3 skills with an empty `id` (the EN textmap hash is missing for that
  language), making them unreachable by slug in CS only.
